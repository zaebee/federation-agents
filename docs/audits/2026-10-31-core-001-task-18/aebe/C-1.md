## 3. Positive evidence

Test: `C-1 orphan ingestion records PARENT_UNRESOLVED in an Assessment`
File: `tests/conformance/c.test.ts`

Graph:

```text
iv-d ──MERGED_FROM──► iv-a   (present)
     └─MERGED_FROM──► iv-b   (absent)
```

The test imports `emitOrphanAssessment` from `src/index.ts`, supplies a caller-owned ID callback, and asserts:

- one registered Assessment;
- `unverified_claims` is exactly `['PARENT_UNRESOLVED']`;
- `parent_version_ids` is `['iv-a', 'iv-b']` — the complete declared parent set;
- `graph.unresolvedParents` is `[['iv-d', ['iv-b']]]`;
- the graph JSON is unchanged;
- the registered representation is frozen.

This is the C-1 positive path. The Assessment is constructed by the adapter, not by a test literal.

## 4. Mixed resolved/unresolved parent evidence

Tests:

- `emits one declaration-scoped assessment for mixed resolved and unresolved parents`
- `assessEdge returns the same assessment for resolved and unresolved edges`

Files:

- `tests/unit/orphan-assessment.test.ts`
- `tests/unit/assessment-validation.test.ts`

The same graph is used. The Assessment contains `['iv-a', 'iv-b']` and `PARENT_UNRESOLVED`. `assessEdge` returns the same Assessment for `iv-d → iv-a` (resolved) and `iv-d → iv-b` (unresolved). The test asserts that `iv-a` is present in the graph and that the claim remains declaration-scoped; it does not assert that `iv-d → iv-a` is unresolved. It also asserts that `evaluateAssurance` for the resolved edge with no required claims is `SATISFIED`, so the unverified declaration-scoped claim is not treated as edge-scoped negative evidence.

This is the explicit distinction required by the approved plan: applicability to an edge does not transform a declaration-scoped claim into an edge-scoped claim. No `assessEdge` behavior was changed and no edge-scoped claim was introduced.

## 5. Negative evidence

Test: `C-1 resolved parent produces no PARENT_UNRESOLVED Assessment`
File: `tests/conformance/c.test.ts`

Graph: `iv-d MERGED_FROM iv-a, iv-b`, both parents present. The adapter returns `assessments: []` and `registered: []`; `graph.unresolvedParents` is empty.

Additional negative cases in `tests/unit/assessment-validation.test.ts`:

- strict subset of the declared parent set → rejected;
- undeclared parent → rejected;
- all parents resolved with a submitted candidate → rejected;
- `PARENT_UNRESOLVED` in `verified_claims` → rejected;
- `CYCLE_DETECTED` in a C-1 candidate → rejected;
- manually constructed graph → rejected;
- `PARENT_UNRESOLVED` through generic `registerAssessment` → rejected.

## 6. Generic vs contextual boundary

Generic `registerAssessment` validates structure and rejects `PARENT_UNRESOLVED` in either claim list. The C-1 contextual path validates the graph relationship and then admits. The tests in `tests/unit/assessment-validation.test.ts` assert both directions.

The `CONTEXT_REQUIRED_CLAIMS` set is admission metadata only. It is not read by `assessEdge`, `evaluateAssurance`, or `Policy`.

## 7. Atomicity and callback boundary

Tests:

- `admits all valid candidates as one frozen representation`
- `admits none when one candidate is invalid`
- `rejects duplicate IDs within the batch`
- `rejects duplicate IDs against existing assessments`
- `rejects unknown supersession references and cycles`
- `leaves the caller existing array and members unchanged on failure`
- `callback failure prevents Core admission and leaves existing unchanged`
- `callback side effects are outside Core atomicity`

Core admission returns either the complete frozen representation or no new representation. `existing` is deep-copied and never mutated. Callback side effects occur before Core admission and are not rolled back; caller-managed persistence occurs only after `ok: true`.

## 8. Graph provenance and Registry limitation

Test: `duplicate version ids with divergent lineage produce a builder-issued combined graph`
File: `tests/unit/lineage-graph.test.ts`

The test pins current structural behavior: duplicate version ids are deduplicated in `nodes`, while both declarations contribute edges. It asserts `isBuiltLineageGraph(graph)` is true. This documents the limitation that builder provenance does not imply descriptor validity; it does not approve contradictory Registry contents.

`buildLineageGraph` remains structural. Descriptor validation is a caller precondition. The C-1 contextual validator checks consistency with the supplied graph, not §5.2 declaration cardinality.

## 9. Package-root surface

Test: `package-root adapter produces the exact C-1 claim through Core admission`
File: `tests/unit/orphan-assessment.test.ts`

The test imports `emitOrphanAssessment` from `src/index.ts`. The adapter calls Core admission. The test also asserts that `registerOrphanAssessment`, `registerOrphanAssessments`, and `validateContinuityAssessment` are exported, and that `isBuiltLineageGraph` is not.

`emitOrphanAssessment` is an experimental reference adapter API. It is not a CORE-001 protocol API and carries no stability guarantee or compatibility commitment.
