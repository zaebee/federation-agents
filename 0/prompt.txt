# Task T18-01 — Assessment Emission Decision Package

## Mode

**Plan Mode only.** Repository investigation and decision-package planning.

Do not implement anything. Do not modify source code, tests, normative specifications, or Task 17 audit artifacts.

## Context

We are working on UIA-CORE-001 Rev 0.3.3.

Task 17 (Full CORE-001 Conformance Verification) is merged. Its final audit must remain historically unchanged.

Task 18 is the approved follow-up: Conformance Gap Disposition & Remediation Roadmap.

The approved Task 18 plan identifies two unresolved decisions:

- **T18-DEC-01:** Does CORE-001 normatively require Assessment emission for the relevant orphan/unresolved-parent and cycle-detection conditions?
- **T18-DEC-02:** If Assessment emission is required, which boundary owns it: CORE-001 Core API or the host adapter?

These decisions affect the remediation path for:

- **C-1:** Assessment emission for an unresolved/orphan parent condition.
- **C-2.a2:** Assessment emission for a cycle-detection condition.
- **C-2.a3:** Application/suppression of dependent grants, which is a separate CORE-003 concern and must not be conflated with Assessment emission.

The current Task 17 statuses are historical facts and must not be rewritten:

- Overall: 152 PASS, 8 PARTIAL, 7 BLOCKED, 8 NOT COVERED, 0 FAIL.
- §12: 13 PASS, 2 PARTIAL, 2 BLOCKED, 1 NOT COVERED.
- C-1 is NOT COVERED.
- C-2 is BLOCKED.
- C-2.a1 (graph cycle detected) is PASS.
- C-2.a2 (Assessment record with `CYCLE_DETECTED`) is NOT COVERED.
- C-2.a3 (dependent grants not applied) is BLOCKED and belongs to a separate authority-boundary question.

Do not reinterpret these historical statuses based on your own preferred architecture.

## Objective

Produce an evidence-backed decision package that allows the project owner to decide:

1. Whether Assessment emission is a normative CORE-001 requirement for C-1 and C-2.a2.
2. If it is required, whether the Core API or host adapter owns emission.
3. What exact decision-register entries should be recorded for T18-DEC-01 and T18-DEC-02.
4. Which remediation branch follows from each possible decision.

This is an investigation and recommendation, not an implementation task. Keep unresolved normative questions OPEN unless the repository provides sufficient evidence to resolve them.

## Questions to answer

### A. Is Assessment emission normatively required?

For each case independently:

**C-1 — unresolved/orphan parent**

- What exact normative text applies?
- Does it require the system to detect the condition only?
- Does it require the condition to be represented as an Assessment?
- Does it specify the Assessment claim, subject, provenance, or emission boundary?
- Is the requirement explicit, implied by normative definitions, or absent/ambiguous?

**C-2.a2 — cycle detection**

- What exact normative text applies?
- Does it require cycle detection only?
- Does it require a `CYCLE_DETECTED` Assessment?
- Does it specify where or by whom this Assessment must be produced?
- Is the Assessment requirement explicit, implied, or absent/ambiguous?

Do not treat a test expectation as normative evidence unless the specification itself establishes the requirement.

Distinguish carefully between:

- detecting a condition;
- constructing an Assessment object;
- emitting/registering an Assessment;
- making an Assessment available to downstream consumers;
- applying a downstream authority or grant consequence.

These are different obligations.

### B. Who owns emission, if required?

Evaluate both ownership models:

**Option 1 — Core API ownership**

The Core API detects the relevant condition and constructs/emits the corresponding Assessment as part of its public behavior.

**Option 2 — Host adapter ownership**

Core exposes sufficient validated information about the condition. The host adapter constructs and emits the Assessment at the integration boundary.

For each option, analyze:

- normative fit with CORE-001;
- consistency with the existing Core API and architecture;
- provenance and trust implications;
- whether the adapter can reliably distinguish the condition without reconstructing hidden internal state;
- whether the implementation would require new public APIs or change existing contracts;
- testability and conformance implications;
- risk of duplicating or contradicting Core validation;
- impact on other consumers of the Core library.

Do not assume that an adapter-owned Assessment is valid merely because an adapter can construct the object.

Do not assume that Core ownership is correct merely because the relevant detection currently happens inside Core.

### C. No normative emission requirement

Explicitly evaluate the third possible outcome:

**Option 3 — CORE-001 does not normatively require Assessment emission.**

If supported by the evidence:

- explain what CORE-001 does require instead;
- explain why C-1 and/or C-2.a2 cannot be treated as implementation gaps;
- identify whether a clarification or normative amendment is still desirable;
- explain the separate specification-change process needed to introduce such a requirement.

Do not silently convert a missing normative requirement into an implementation task.

### D. Relationship to C-2.a3

Keep C-2.a3 separate throughout.

Assessment emission (`C-2.a2`) does not prove that dependent grants are suppressed (`C-2.a3`).

An Assessment object does not itself create, revoke, or suppress authority.

Identify the CORE-003 dependency and explain why resolving T18-DEC-01/02 cannot independently close C-2.

# T18-01 Supplement — Adapter Boundary and Assessment Contract

Continue the existing T18-01 investigation. Do not rewrite the package from scratch.

The current recommendation is adapter-owned Assessment emission, but the investigation identified unresolved architectural questions that must be addressed before the decision package is ready for approval.

## 1. Public API verification

Verify whether `registerAssessment` is actually exported through `src/core/index.ts`.

Distinguish:

- public package API;
- internal module export;
- test-only/internal helper.

Trace the import path an external host adapter would use.

If the adapter must import an internal module, explicitly identify this as an API boundary gap.

Do not describe an internal module export as an existing public integration contract.

## 2. Assessment validation boundary

The current implementation analysis says `registerAssessment` performs copy/freeze and duplicate/supersession checks but does not validate Assessment fields.

Investigate:

- which fields are structurally validated today;
- which invariants are checked;
- which invariants are not checked;
- whether malformed Assessment objects can be registered;
- whether any other public API validates these objects.

Evaluate three possible validation owners:

A. Core validator, called by the adapter.

B. Host adapter performs validation under a normative contract.

C. Assessment construction and validation are both owned by Core.

For each option, identify required APIs, invariants, and tests.

Do not assume that deep copy/freeze constitutes semantic validation.

## 3. Define the minimum Assessment contract

Analyze C-1 and C-2 separately.

For C-1, identify the minimum information necessary to represent an unresolved-parent condition.

For C-2, compare:

- one Assessment per SCC;
- one Assessment per cycle node;
- one Assessment per affected lineage edge.

For each model, discuss subject identity, parent references, provenance, determinism, duplicate handling, and downstream interpretation.

Do not silently choose one model. If CORE-001 does not specify it, mark it as an explicit specification question.

## 4. Reconcile normative obligation and implementation ownership

Clarify the distinction between:

- the normative obligation for a local assessment to record a condition;
- the mechanism that constructs the Assessment;
- the mechanism that validates it;
- the mechanism that registers or exposes it.

Propose a more precise wording for DEC-01 and DEC-02.

DEC-01 may be recommended for approval based on the cited normative text, but do not mark it approved.

DEC-02 must remain OPEN unless the public API and validation boundary are sufficiently established.

## 5. Reassess AEBE

Update AEBE acceptance criteria so that they explicitly identify:

- Assessment construction owner;
- Assessment validation owner;
- registration/publication mechanism;
- public API used;
- positive and negative test evidence;
- provenance and reproducibility requirements.

A hand-constructed test fixture is not sufficient evidence of actual boundary behavior.

## 6. Deliverable

Create a supplemental section in the existing T18-01 package:

`boundary-and-contract-analysis.md`

Also propose minimal amendments to the existing decision recommendation and remediation branch map.

Do not modify source, tests, CORE-001, Task 17 artifacts, or existing Task 18 decisions.

Do not create implementation tasks yet.

Keep all decisions OPEN and report any evidence that could not be verified.
