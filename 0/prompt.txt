## 2. Normative source and implementation boundaries

#### Path Discovery requirements

Given a candidate IdentityVersion and an origin IdentityVersion:

1. Validate the target Participant.
2. Validate version scheme and selector expression.
3. Search for permitted paths from candidate to origin.
4. Respect the selected LineageTraversalScope.
5. Evaluate applicable assessments on path edges.
6. Reject paths with missing or conflicting required assessments.

#### Merge Closure requirements

Whenever a selected path traverses a MERGED_FROM node:

- Validate every parent edge of that merge node.
- Validate branches even when they do not lead to the requested origin.
- Do not silently ignore an unvalidated branch.
- Reject the selected path if any required parent branch fails assurance.

A candidate is eligible if at least one permitted path to the origin exists, every edge on that path satisfies assurance, and every parent edge of every MERGED_FROM node encountered on that path satisfies merge closure requirements.

Do not enumerate all possible paths if that creates exponential complexity.

You may use memoization, dynamic programming or another equivalent algorithm, but the result MUST be semantically equivalent to the specification.

The result MUST NOT depend on:

- edge insertion order;
- node storage order;
- traversal implementation details;
- arrival order of an otherwise identical final set of declarations and assessments.

If you discover ambiguity in the specification that changes observable results, do not silently choose an interpretation. Document it and request clarification.

## 1. Блокеры

### 1.1. `trusted: false` ошибочно превращается в `TEMPORAL_TRUST_UNASSESSED`

Это самая существенная проблема.

Сейчас Global Constraint 10 говорит:

> absent, NOT_ASSESSED, or trusted:false → trust-unresolved outcome

Но эти три состояния не эквивалентны:

| Состояние                  | Что известно                                     |
| -------------------------- | ------------------------------------------------ |
| Нет результата             | Доверие не оценивалось или результат недоступен  |
| `NOT_ASSESSED`             | Явно зафиксировано отсутствие оценки             |
| `ASSESSED, trusted: false` | Оценка проведена, timestamp признан недоверенным |
| `ASSESSED, trusted: true`  | Timestamp признан доверенным                     |

`trusted: false` — это не отсутствие оценки. Это отрицательный результат оценки.

Если свести его к `TEMPORAL_TRUST_UNASSESSED`, система теряет важное различие между неизвестно и установлено, что доверять нельзя. Это противоречит общей эпистемической модели UIA, в которой отсутствие знания и отрицательное установление не должны сливаться.

Предлагаю разделить результаты:

```
type TemporalTrustOutcome =
  | { status: 'TRUSTED' }
  | { status: 'UNTRUSTED'; assessment: AssessedTrustResult }
  | { status: 'UNASSESSED' }
  | { status: 'TRUST_ASSESSMENT_UNAVAILABLE' };
```

При этом не нужно заранее придумывать, что делать с каждым исходом на уровне всех операций. Достаточно сохранить различия в типах и передать локальной политике решение о допустимости.

A-9 остаётся BLOCKED в части механизма оценки доверия. Но это не основание терять уже полученную информацию о результате оценки.

### 1.2. `evaluateAssurance` всё ещё допускает рассогласование EdgeRef

В интерфейсе:

```
function evaluateAssurance(
  edgeRef: EdgeRef,
  applicable: SSApplied,
  requirement: ContinuityAssuranceRequirement,
  policy: Policy,
  ctx: TemporalContext
): AssuranceResult;
```

И одновременно:

```
type SSApplied = {
  edge: EdgeRef;
  assessments: readonly DeepReadonly<ContinuityAssessment>[];
  unresolved: boolean;
};
```

Получается, что одна и та же функция получает два EdgeRef. Что произойдёт, если:

```
edgeRef = { child: 'A', parent: 'B', relation: 'CONTINUATION' }

applicable.edge = {
  child: 'X',
  parent: 'Y',
  relation: 'FORKED_FROM'
}
```

Это не просто теоретический вопрос: именно против edge substitution мы вводили edge-bound assurance.

Нужно выбрать один из двух контрактов:

1. `evaluateAssurance` принимает только `ApplicableAssessments`, в котором EdgeRef уже связан с результатом, а объект создаётся исключительно через `assessEdge`.
2. Функция принимает оба значения, но обязана проверить их полное структурное равенство и вернуть типизированную ошибку при несовпадении.

Я предпочёл бы первый вариант: меньше возможностей для некорректного состояния.

Есть ещё один связанный момент: `Policy.applicableAssessments` может вернуть произвольный список. Если это hook только для выбора применимых оценок, он должен иметь право сузить множество, но не расширить его за счёт assessment, относящегося к другому edge. Повторная проверка subject/relation/parent должна оставаться ответственностью core.

### 1.3. Доверие к `signed_at` не должно обходиться через D-3

В Rev C написано:

> compromise-time logic uses revocation + local policy acceptance, not signed_at trust

Но D-3 сравнивает:

```
signed_at = 100
compromise_effective_at = 80
```

и ожидает:

```
historical signature = INVALID
```

Для такого вывода необходимо знать, что сравниваемое время подписи достоверно. Иначе можно получить математически корректное сравнение двух чисел, но не обоснованный исторический вывод.

Здесь нельзя одновременно утверждать:

- `signed_at` не доверен;
- `signed_at` не нужен для определения исторической валидности;
- подпись была сделана после момента компрометации.

Это нужно развести.

Предлагаю: D-3 даёт `INVALID` только при наличии достаточного основания доверять обоим временным значениям в рамках локальной политики. Если доверие к `signed_at` отсутствует, результат должен сохранять неопределённость, а не выдавать `INVALID`.

Иначе новый temporal trust model сам себе противоречит.

Дополнительно `AssessedTrustResult` должен быть привязан к конкретному timestamp: как минимум к его значению и типу (`SIGNED_AT` и т. п.). Сейчас результат доверия можно потенциально повторно применить после изменения значения timestamp. Для внешнего механизма оценки это опасный контракт.

### 2.2. Canonicalization: есть ещё один способ незаметно потерять данные

Вы хорошо расширили список отклоняемых значений. Но в нём не вижу явного запрета на non-enumerable own string properties.

Например:

```
const value = { a: 1 };

Object.defineProperty(value, 'b', {
  value: 2,
  enumerable: false
});
```

Обычная сериализация может пропустить `b`. Тогда объект содержит данные, которые не попали в hash, хотя вызывающий код мог считать их частью descriptor.

Нужно явно решить: отклонять любые собственные string properties, которые не являются enumerable, или определить другой строгий контракт.

Также проверьте аналогичную ситуацию с дополнительными свойствами массива: sparse arrays вы запретили, но нужно исключить незаметное игнорирование нестандартных own properties.

### Medium finding

**Location:** `src/core/ownership.ts:247-252`

The new `validateJsonValue` builds its output with `out[key] = r.value` on an ordinary `{}` literal. For untrusted JSON such as `JSON.parse('{"__proto__":{"isAdmin":true}}')`, this calls the `__proto__` setter instead of storing a data key. The "validated" JsonValue then has an attacker-chosen prototype: `out.isAdmin === true` is inherited, while `Object.keys(out)` is `[]`. This function is the strict JSON gate for spec-required JSON values. Its output can therefore carry inherited fields that downstream checks will read, and the key-based checks inside the function never inspected those fields. Reproduced at head. Build `out` with `Object.defineProperty`/`Object.fromEntries`, or reject the `__proto__` key.
