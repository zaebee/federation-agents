## Goal

Implement the first two independently testable traversal phases:

1. **Path Discovery** — find paths permitted by the selected traversal scope.
2. **Path Validation** — evaluate every edge of one concrete path against the assurance requirement.

Expose an orchestration API `evaluateBinding(policy, ctx)` that composes these phases.

The implementation must be deterministic, pure, immutable, and independent of Bun/Node runtime APIs.

**Merge Closure Validation is explicitly out of scope. It belongs to Task 10.**

## 1. Public API and phase boundaries

Follow the approved API shape in the implementation plan. Adapt only where existing repository types require it; do not silently change semantics.

Expected interfaces:

```ts
function discoverPaths(
  graph: LineageGraph,
  scope: LineageTraversalScope,
  candidateID: IdentityVersionID,
  originID: IdentityVersionID,
): Result<PathSet>;

function validatePath(
  path: Path,
  requirement: ContinuityAssuranceRequirement,
  policy: Policy,
  ctx: TemporalContext,
): Result<PathValidation>;

function evaluateBinding(
  state: {
    graph: LineageGraph;
    descriptors: readonly IdentityVersionDescriptor[];
  },
  binding: ConditionalVersionBinding,
  candidateID: IdentityVersionID,
  policy: Policy,
  ctx: TemporalContext,
): BindingResult;
```

The exact exported types must be strongly typed, immutable, and consistent with the existing project conventions.

### Phase 1 — `discoverPaths`

Input:
- an existing `LineageGraph`;
- a `LineageTraversalScope`;
- candidate version ID;
- origin version ID.

Responsibilities:

1. Traverse only edges permitted by the selected `traversal_scope`.
2. Follow the direction of lineage: candidate → parent → … → origin.
3. Discover all relevant candidate-to-origin paths.
4. Treat cycles as dead ends / structural conflicts, not as a reason to crash.
5. Do not treat unresolved parent references as registered graph nodes.
6. Return `ERR_NO_TRAVERSAL_PATH` if no permitted path exists.
7. If multiple paths exist, preserve them as independent paths. Multiple paths are not themselves an error.
8. Ensure deterministic ordering independent of graph storage order.

The implementation plan calls for memoized, sorted DFS. Use an equivalent approach only if it preserves the required behavior and does not introduce unnecessary complexity.

**Critical phase boundary:** Path Discovery must not inspect assessments, invoke `assessEdge`, invoke `evaluateAssurance`, or make assurance decisions.

It answers reachability under the selected scope, nothing more.

### Phase 2 — `validatePath`

Input:
- one concrete `Path`;
- `ContinuityAssuranceRequirement`;
- required `Policy`;
- required `TemporalContext`.

For every edge in this particular path:

1. Verify that the edge is permitted by the applicable traversal scope / path contract.
2. Call `assessEdge()` with the exact edge binding.
3. Pass the resulting `ApplicableAssessments` to `evaluateAssurance()`.
4. Preserve the exact assurance outcome and relevant details.
5. Fail if an edge has no applicable assessment or does not satisfy the requirement.

Follow §8.5 literally:

- every path edge must have an applicable `ContinuityAssessment`;
- every edge must satisfy the assurance requirement;
- applicable disqualifying Claims must not be ignored;
- unresolved applicable conflicts must not be treated as success;
- absence of an Assessment is never success.

Use Task 8 APIs. Do not reimplement assessment applicability, trust filtering, policy narrowing, or assurance semantics inside traversal.

**Important:** `validatePath()` validates only the supplied path. It must not silently inspect sibling branches or perform merge closure.

### Orchestration — `evaluateBinding`

Compose the phases:

1. Perform the required §8.3 preliminary checks.
2. Discover permitted paths.
3. Validate each discovered path independently.
4. Return an eligible result if at least one path passes the phases implemented in this task.
5. Preserve failures and their per-path context in the result.

`Policy` and `TemporalContext` are mandatory explicit parameters. No global policy, hidden state, implicit temporal context, or default trust-all behavior.

The `BindingResult` must follow the approved plan's discriminated union. Do not expose partially eligible results or use bare booleans for semantic failures.

**Task 9 limitation:** this orchestration does not yet perform Phase 3 (Merge Closure Validation). Task 10 will complete that part. Do not claim full §8 conformance after Task 9 alone.

Both decisions are approved. Record them as explicit Task 9 implementation decisions, not as pre-existing signatures from the approved plan.

### Decision 1 — explicit Assessment input

The original Task 9 signatures have a blocking data-flow gap: `assessEdge()` requires candidate Assessments, but no approved input provides them.

Adopt these signatures:

```ts
function validatePath(
  path: Path,
  assessments: readonly ContinuityAssessment[],
  requirement: ContinuityAssuranceRequirement,
  policy: Policy,
  ctx: TemporalContext,
): Result<PathValidation>;

function evaluateBinding(
  state: {
    graph: LineageGraph;
    descriptors: readonly IdentityVersionDescriptor[];
    assessments: readonly ContinuityAssessment[];
  },
  binding: ConditionalVersionBinding,
  candidateID: IdentityVersionID,
  policy: Policy,
  ctx: TemporalContext,
): BindingResult;
```

`discoverPaths()` remains unchanged and independent of Assessments.

For every edge, `validatePath()` passes the explicit Assessment set to Task 8's `assessEdge()`. Task 8 remains the sole owner of assessment applicability and edge binding. No global state, hidden registry, implicit data source, or duplicate applicability logic.

Do not mutate or retain caller-owned Assessment arrays. Missing applicable Assessments must never count as success.

### Decision 2 — all-CONTESTED aggregation

Add a distinct implementation-level `BindingResult` variant:

```ts
{
  eligible: false;
  kind: 'CONTESTED';
  details: {
    perPath: readonly FailedPath[];
  };
}
```

This is not a new `UiaErrorCode` and must not be represented as `ERR_ASSURANCE_PREDICATE_UNSATISFIED`.

For this Task 9 implementation:
- At least one VALID path → `eligible: true`.
- No VALID paths, but at least one CONTESTED path → `kind: 'CONTESTED'`.
- Ordinary normative failures retain their normative codes.
- Mechanism failures remain distinct and must not be silently mapped to normative errors.

This is a Task 9 implementation-level aggregation decision only. It does not close A-8 or establish a general normative error-precedence table. Preserve all per-path outcomes. If a combination cannot be represented without inventing additional semantics, stop and report it.
