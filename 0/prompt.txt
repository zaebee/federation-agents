### Medium finding

**Location:** `src/core/traversal.ts:206`

Under `FULL_ANCESTRY`, a merge with k distinct parents that each reach the origin incurs Θ(k²) comparisons in this deduplication loop. Merge cardinality is unbounded (`src/core/lineage.ts:44`), and discovery builds adjacency for the whole origin-reachable graph (`src/core/traversal.ts:304–309`), so a wide merge can stall even an unrelated one-edge lookup. Use per-child sets keyed by parent and relation for linear deduplication. 
---
### Medium finding

**Location:** `src/core/traversal.ts:276-278`

When `evaluateBinding` invokes discovery (`src/core/traversal.ts:543`) on a long linear CONTINUATION chain, every active frame retains a complete edge prefix and visited set, requiring Θ(n²) live storage for one path. A 10,000-edge chain retains roughly 50 million entries in each structure before validation starts, risking heap exhaustion despite linear input and output sizes. Maintain one backtracked path and visited set, copying only when emitting a completed path. 
---
### Medium finding

**Location:** `src/core/traversal.ts:199-238`

`discoverPaths` lists every simple candidate→origin path and keeps them all in memory, with no limit on path count or depth. `evaluateBinding` then runs `validatePath` on each one, which deep-copies all assessments for every edge. A participant who publishes descriptors forming a chain of k merge diamonds (`MERGED_FROM` under `FULL_ANCESTRY`, about 3k nodes) produces 2^k paths, so evaluating a binding for their candidate can hang or run out of memory. Fix: cap the number of paths and the work done, returning a mechanism failure when the cap is hit, or answer reachability and validity without listing every path.

`evaluateBinding` передаёт `state.assessments`. Никакого глобального состояния. Task 8 остаётся единственным владельцем applicability и assurance semantics.

2\. `MergeClosureResult` и причины отказа

Принимаем предложенные discriminated unions без новых normative error codes:

```
type MergeClosureBranchFailure =
  | {
      readonly branch: EdgeRef;
      readonly reason: 'NO_APPLICABLE_ASSESSMENT';
    }
  | {
      readonly branch: EdgeRef;
      readonly reason: 'ASSURANCE_UNSATISFIED';
      readonly missing: readonly string[];
      readonly disallowed: readonly string[];
    }
  | {
      readonly branch: EdgeRef;
      readonly reason: 'CONTESTED';
      readonly contestedClaims: readonly string[];
    };

type MergeClosureResult =
  | { readonly status: 'SATISFIED' }
  | {
      readonly status: 'UNSATISFIED';
      readonly code: 'ERR_MERGE_BRANCH_UNSATISFIED';
      readonly failures: readonly MergeClosureBranchFailure[];
    };
```

Собирать все неудачные closure-only ветви, сортировать по `(child, parent)`. `MechanismFailure` не превращать в branch failure: он должен оставаться отдельным результатом `Result`.

3\. `PathOutcome.closure` и GC-18

Принимаем:

```
interface PathOutcome {
  readonly path: Path;
  readonly outcome: PathValidation;
  readonly closure?: MergeClosureResult;
}
```

`details.perPath` — `readonly PathOutcome[]` и в success-, и в failure-вариантах `BindingResult`.

`FailedPath` можно оставить экспортированным для совместимости, но не использовать как тип `details.perPath`: closure failure может относиться к пути с `outcome: VALID`.

Это необходимое расширение публичного типа, а не изменение семантики `PathValidation`. Не переписывать `VALID` в `INVALID` только ради того, чтобы представить closure failure.

4\. Порядок агрегации

Принимаем ровно этот порядок:

1. Есть путь с `VALID` + `closure: SATISFIED` → `eligible: true`.
2. Иначе есть `closure: UNSATISFIED` → `ERR_MERGE_BRANCH_UNSATISFIED`.
3. Иначе есть `CYCLE_DETECTED` → `CYCLE_DETECTED`.
4. Иначе есть `CONTESTED` → `kind: 'CONTESTED'`.
5. Иначе — обычный assurance failure.

Это локальный порядок агрегации Task 10. A-8 остаётся OPEN. Успешный путь без вычисленной closure не должен случайно считаться eligible там, где closure требуется.

5\. Branch failure semantics

Принимаем:

- `NO_APPLICABLE_ASSESSMENT` — `assessEdge` не дал применимого Assessment для closure-only ребра.
- `ASSURANCE_UNSATISFIED` — применимый Assessment есть, но `evaluateAssurance` вернул `UNSATISFIED`; сохраняются `missing` и `disallowed`.
- `CONTESTED` — assurance вернул `CONTESTED`; сохраняются `contestedClaims`.
- Ошибки механизма остаются `MechanismFailure`, не маскируются под эти три причины.

B-5 — отдельный conformance case для `assessEdge`/`evaluateAssurance`, не closure failure. Ожидаемый результат — `ERR_ASSURANCE_PREDICATE_UNSATISFIED`; untrusted positive Assessment не может компенсировать отсутствие подтверждения от trusted assessor.
