# Task 18 — CORE-001 Conformance Gap Disposition & Remediation Roadmap

## Mode

**Plan Mode only. Do not implement anything.**

Produce a reviewable remediation roadmap based on the completed Task 17 audit. This task is about disposition, prioritization, dependencies, and acceptance criteria — not about immediately fixing every non-PASS item.

- `docs/CORE-001.md` — UIA-CORE-001 Rev 0.3.3 (normative specification).

## Objective

Produce a technically justified, dependency-aware roadmap for resolving or explicitly retaining every non-PASS item identified by Task 17.

The roadmap must answer:

1. What exactly is missing?
2. Is the gap in implementation, tests/evidence, normative specification, cross-spec integration, or an external responsibility?
3. What is the smallest valid action that addresses it?
4. What must happen before that action?
5. What evidence would justify changing its status?
6. Which items should deliberately remain BLOCKED, NOT COVERED, or PARTIAL?

## Mandatory principles

### 1. Preserve normative boundaries

Do not silently resolve normative ambiguity through implementation choices.

In particular:

- Preserve all existing A-1…A-12 ambiguity dispositions.
- Do not convert a BLOCKED item into an implementation task unless the necessary normative decision has been made separately.
- Do not infer new semantics from existing implementation behavior.
- Do not introduce new authority, grant, revocation, or acceptance semantics without an explicit specification-level decision.
- Do not add a grant-producing API to CORE-001.
- Do not conflate Evidence, Finding, Ruling, and Execution Authorization.
- Do not treat identity continuity as authority inheritance.
- Do not treat cryptographic signature validity as proof of actor identity, intent, authority, or runtime legitimacy.

### 2. Distinguish gap categories

For every non-PASS item, assign one primary disposition category:

- `IMPLEMENTATION_GAP` — normative behavior is clear, implementation is missing or incorrect.
- `TEST_GAP` — implementation may be correct, but evidence is insufficient.
- `SPECIFICATION_DECISION` — normative ambiguity or missing normative rule requires a separate decision.
- `CROSS_SPEC_DEPENDENCY` — responsibility belongs to another UIA specification or integration boundary.
- `EXTERNAL_DEPENDENCY` — responsibility belongs to an external system, operator, or infrastructure.
- `DOCUMENTATION_GAP` — behavior exists but documentation is insufficient or inaccurate.
- `INTENTIONAL_LIMITATION` — current scope deliberately does not provide this capability.
- `UNRESOLVED` — insufficient information to classify safely.

A secondary category may be recorded where necessary.

Do not label an implementation gap as a test gap merely because a test is also missing. Conversely, do not claim an implementation defect solely because a test is absent.

### 3. Preserve audit traceability

Every roadmap entry must reference:

- Task 17 requirement ID (`N-###`) or readiness item.
- Relevant conformance assertion ID (`CASE-*`) where applicable.
- Relevant ambiguity ID (`AMBIG-*`) where applicable.
- Relevant Task 17 finding/register ID (`T-*`, if applicable).
- Exact source file and relevant code/test location, when known.

Do not invent IDs. If an audit item has no suitable identifier, explicitly flag that as a traceability gap.

### 4. Do not optimize for a PASS count

The goal is correct conformance and honest evidence, not maximizing the number of PASS labels.

A valid final state may contain BLOCKED, NOT COVERED, PARTIAL, or intentional limitations.

Do not propose superficial tests that merely reproduce implementation behavior or assert constants without proving the normative property.

## Required analysis

### A. Reconcile all non-PASS items

Read the Task 17 artifacts and enumerate every non-PASS item.

Reconcile the totals against the audit matrices. Do not rely only on the summary rollups.

For each item, explain:

- Current status.
- What the requirement actually demands.
- What the implementation currently provides.
- What evidence currently exists.
- What is missing.
- Primary disposition category.
- Recommended next action.
- Whether the action changes code, tests, specification, documentation, or an external system.
- Whether a separate approval or normative decision is required.

If the audit artifacts contain inconsistent classifications or unsupported conclusions, flag them. Do not silently rewrite the audit's conclusions.

### B. Reassess implementation versus evidence

Pay particular attention to these known areas, without assuming that the previous audit conclusion is necessarily final:

- Descriptor digest computation versus actual digest verification (N-084).
- Downstream decision enforcement versus conflict detection (N-079).
- Runtime lifecycle and the meaning of a constant `RUNNING` state (D-1 / N-004).
- Version-label validation boundary (N-019 / F-005).
- Historical signature evaluation and future authorization policy boundaries (D-4 / T-004).
- C-1 / C-2 partial graph-level evidence versus missing assessment-level conformance.
- §14–§16 runtime, boundary, and readiness requirements.

For each, determine whether the smallest appropriate next step is:
- a test,
- an implementation change,
- a specification decision,
- a separate specification/task,
- an external integration,
- or no action beyond documenting the limitation.

Do not assume a missing test proves a defect.

### C. Build a dependency graph

Group proposed work into coherent tasks.

For every proposed task provide:

- Task ID and title.
- Objective.
- Included requirement IDs.
- Explicit exclusions.
- Prerequisites.
- Dependencies on other tasks/specifications.
- Expected source areas.
- Deliverables.
- Acceptance criteria.
- Required verification commands.
- Whether the task is implementation, test-only, documentation-only, or specification work.
- Whether it requires normative approval.

Identify parallelizable tasks and critical-path dependencies.

Avoid creating artificial tasks for items that should remain blocked or intentionally out of scope.

### D. Prioritize

Use explicit criteria rather than intuition:

1. Normative correctness and risk of violating CORE-001.
2. Security and authority-boundary implications.
3. Impact on downstream specifications or consumers.
4. Whether the requirement is already sufficiently implemented but under-tested.
5. Dependency leverage.
6. Cost and scope of the smallest valid remediation.

Provide a priority (`P0`–`P3`) and explain it.

Do not classify every security-adjacent item as P0 automatically.

### E. Define closure criteria

For each proposed remediation task, state what evidence is sufficient to close it.

Examples:

- A test must demonstrate the normative property, including relevant adversarial cases.
- An implementation change must be tied to a clear normative requirement.
- A specification decision must be recorded as an explicit approved normative change, not inferred from code.
- A cross-spec dependency must identify the receiving specification and its responsibility.
- An external dependency must identify the external actor/system and what evidence is expected from it.

Specify which Task 17 status transitions are justified by which evidence.
