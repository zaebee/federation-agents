## 2. Version scheme validation

Implement validation for the three schemes defined by the specification:

### SEMVER_2

Use Semantic Versioning 2.0.0 rules.

Test against official SemVer 2.0.0 valid and invalid examples, including:

- valid core versions;
- prerelease identifiers;
- build metadata;
- numeric identifier restrictions;
- malformed versions;
- leading-zero restrictions;
- invalid characters and separators.

Do not implement a permissive approximation of SemVer.

The validator must distinguish valid labels from invalid labels according to the SemVer 2.0.0 grammar.

### CONTENT_HASH

The only currently specified validation rule is **non-empty**.

Important: Ambiguity A-7 remains OPEN. The normative specification does not define the label format.

Therefore:

- accept any non-empty label that satisfies the applicable general input constraints;
- reject an empty label;
- do not assume hexadecimal encoding;
- do not require a particular digest algorithm;
- do not infer a hash length;
- do not reuse the descriptor hash URN format as a CONTENT_HASH label format.

Do not resolve A-7 in implementation code.

### OPAQUE_TAG

The only currently specified validation rule is **non-empty**.

Important:

- opaque tags have no ordering semantics;
- do not parse them as SemVer;
- do not compare them lexicographically to establish version precedence;
- do not infer ordering from timestamps or insertion order.

Exact equality is meaningful; version ordering is not.

## 3. Versioned selector mechanism

Implement the minimal selector mechanism identified in the approved plan.

Mechanism version:

`uia-ref-selector@1`

This is an implementation mechanism, not normative UIA protocol semantics.

The supported grammar is:

- `=x` — exact match;
- `*` — wildcard, matches all labels;
- `>x`
- `>=x`
- `<x`
- `<=x`
- `^x`
- `~x`
- multiple comparators joined with `&&`.

Examples of supported forms:

- `=1.2.3`
- `*`
- `>=1.2.0&&<2.0.0`
- `^1.2.3`
- `~1.2.3`

Read §8.2 and the plan carefully before choosing parsing and matching details.

### Scheme compatibility

For `SEMVER_2`:

- exact selectors and wildcard are supported;
- comparator/range selectors are supported according to the mechanism grammar;
- comparisons must use SemVer semantics, not string ordering.

For `OPAQUE_TAG` and `CONTENT_HASH`:

- exact-match selectors are supported;
- wildcard is supported;
- range/comparator selectors are incompatible.

An incompatible selector/scheme combination MUST return a `MechanismFailure` with code:

`S_SELECTOR_INCOMPATIBLE_SCHEME`

It MUST NOT be represented as a `SpecFailure`, `UiaErrorCode`, or normative protocol state.

Do not silently reinterpret an incompatible selector as exact match or wildcard.

### Parsing and matching

Keep parsing separate from matching:

- `compileSelector` parses and validates a selector for a given version scheme;
- `selectorMatches` evaluates a compiled selector against a version label.

Use explicit typed structures for compiled selectors. Do not expose `any` or unvalidated `unknown` in public records or semantic results.

Malformed selector syntax must be rejected deterministically. Follow existing Result/Failure conventions and keep mechanism errors separate from normative errors.

Do not add unsupported syntax, aliases, OR operators, escaping rules, or implicit coercions.

## API shape

Use the proposed API:

```ts
type VersionLabel = {
  readonly scheme: VersionScheme;
  readonly label: string;
};

validateVersionLabel(
  value: unknown,
  scheme: VersionScheme,
): Result<VersionLabel>;

const SELECTOR_MECHANISM_VERSION = 'uia-ref-selector@1';

type CompiledSelector = {
  readonly mechanism: 'uia-ref-selector@1';
  readonly scheme: VersionScheme;
  readonly kind: 'WILDCARD' | 'COMPARATORS';
  readonly comparators: readonly {
    readonly op: '=' | '>' | '>=' | '<' | '<=' | '^' | '~';
    readonly version: SemVer;
  }[];
};

compileSelector(
  value: unknown,
  scheme: VersionScheme,
): Result<CompiledSelector>;

selectorMatches(
  selector: CompiledSelector,
  label: VersionLabel,
): boolean;
```

Records and nested arrays must be owned and deeply frozen. Keep `SemVer` internal or expose it only as a properly typed immutable structure if required by the public API. Do not expose mutable parser internals.

`selectorMatches` returns false for scheme mismatch.

## Approved mechanism decisions

1. For `SEMVER_2`, `=` is full string equality, including build metadata. `=1.2.3` does not match `1.2.3+build.5`.
2. Range comparison uses SemVer 2.0.0 precedence. Do not apply npm's prerelease gating. For example, `>=1.0.0` matches `1.1.0-alpha` because SemVer precedence places it above `1.0.0`.
3. Comparators accept only full SemVer versions: `1.2.3`. Reject partial versions, wildcards, and `v` prefixes.
4. Expand `^` and `~` into lower-inclusive and upper-exclusive bounds during compilation:
   - `^1.2.3` → `>=1.2.3 && <2.0.0`
   - `^0.2.3` → `>=0.2.3 && <0.3.0`
   - `^0.0.3` → `>=0.0.3 && <0.0.4`
   - `~1.2.3` → `>=1.2.3 && <1.3.0`
5. Trim the whole selector expression and each `&&` segment. Reject empty segments and internal whitespace inside a comparator. `*` is only valid as the complete expression.
6. CONTENT_HASH and OPAQUE_TAG accept any non-empty string, without trimming or format/length/algorithm assumptions. Reject lone surrogates. OPAQUE_TAG is never parsed or ordered as SemVer.
7. Compare arbitrarily large SemVer numeric identifiers without converting them to imprecise JavaScript numbers. Use digit-string length followed by lexicographic comparison.
8. Upper-bound calculation for `^` and `~` must not silently lose precision. Detect unsafe numeric increment and return a deterministic mechanism failure rather than producing a wrong bound.
