## 2. Найденные замечания

### P1 — `createRuntimeRegistry` не валидирует внешний массив

Файл: [`src/core/runtime.ts`](https://github.com/zaebee/federation-agents/blob/b94fb05076f336751c8d033a91be366355627863/src/core/runtime.ts?utm_source=chatgpt.com)

Сейчас:

```
export function createRuntimeRegistry(value: unknown): Result<RuntimeRegistry> {
  if (!Array.isArray(value)) {
    return invalid('$', 'expected array of RuntimeInstanceDescriptor values');
  }

  // ...
  for (let index = 0; index < value.length; index += 1) {
    const validated = validateRuntimeInstanceDescriptor(value[index]);
```

Проблема: каждый descriptor валидируется через `validateRuntimeInstanceDescriptor`, но сам массив не проходит `validateJsonValue`.

Это означает, что внешний контейнер может содержать неподдерживаемые структуры, которые строгий JSON validator должен отклонять:

- дополнительные собственные свойства массива;
- symbol properties;
- нестандартный prototype;
- нестандартные дескрипторы свойств;
- accessor properties.

Например:

```
const runtimes = [validRuntime];
(runtimes as unknown as Record<string, unknown>).metadata = 'unexpected';

createRuntimeRegistry(runtimes);
```

Сейчас такой массив потенциально будет принят, потому что цикл проверяет только индексированные элементы.

Это расходится с Global Constraint 5: boundary validation должна отвергать неподдерживаемые структуры.

Исправление: сначала валидировать весь `unknown` через `validateJsonValue`, затем проверять, что полученное значение — массив, и работать уже с валидированной копией.

```
const json = validateJsonValue(value);
if (!json.ok) return json;

if (!Array.isArray(json.value)) {
  return invalid('$', 'expected array of RuntimeInstanceDescriptor values');
}
```

Добавить тесты на extra properties, symbol properties и нестандартный prototype массива.

### P2 — несогласованная валидация RuntimeInstanceID

В `entities.ts` существующий `validateRuntimeInstanceDescriptor` проверяет ID через `requireString`, то есть допускает пустую строку.

В `runtime.ts` `createRuntimeLifecycleEvent` использует собственный `requireString`, который требует непустую строку.

В результате возможна ситуация:

1. Registry успешно регистрирует RuntimeInstance с `id: ''`.
2. Event с `runtime_instance_id: ''` создать нельзя.
3. Зарегистрированный runtime невозможно адресовать через lifecycle event.

Нужно согласовать правила валидации.

Я бы не вводил новое ограничение формата идентификаторов только в Task 14. Лучше придерживаться уже существующего контракта `validateRuntimeInstanceDescriptor`, если нормативная спецификация не устанавливает дополнительного ограничения.

### P2 — conformance test не полностью связывает IdentityVersion с runtime

Файл: [`tests/conformance/d.test.ts`](https://github.com/zaebee/federation-agents/blob/b94fb05076f336751c8d033a91be366355627863/tests/conformance/d.test.ts?utm_source=chatgpt.com)

Тест создаёт IdentityVersion:

```
const identity = descriptor({
  id: 'iv-a-1',
  participant: 'participant-a',
  versionLabel: '1.0.0',
});
```

Затем создаёт два RuntimeInstance, ссылающихся на `iv-a-1`.

Снимок IdentityVersion сравнивается до и после операции, что полезно. Но сама связь между зарегистрированной версией и runtime явно не проверяется.

Я бы добавил assertion:

```
expect(updated.runtimes().every(
  runtime => runtime.identity_version_id === identity.id
)).toBe(true);
```

Это небольшое усиление conformance test: он будет проверять не просто неизменность отдельного объекта, но и соответствие сценария D-1.

## 3. Что сделано хорошо

Несколько важных решений я отдельно проверил.

Branding. Registry и Event действительно защищены runtime-проверкой через `WeakSet`. Простого structural object недостаточно, чтобы пройти `recordRuntimeEvent`.

Ownership. `recordRuntimeEvent` не использует прежние ссылки на descriptors и events: они копируются и повторно замораживаются. Исходный registry остаётся неизменным.

Разделение event/state. `stateOf()` возвращает `RUNNING` для обоих runtime независимо от наличия FAILURE event. Это соответствует согласованной минимальной модели, а не случайному пропуску перехода.

Отсутствие deduplication. Два одинаковых события сохраняются как два события. Это правильно: CORE-001 не определяет event identity.

CORE-002. Нет timestamp, sequence, event ID, replay, delivery или persistence semantics. Агент не начал проектировать следующий протокол внутри текущей задачи.
