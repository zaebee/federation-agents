## Что я бы уточнил

### 1. Уточнить инвариант backtracking

Формулировка `frame = { node, next }` допустима, но важно явно зафиксировать правило:

- при переходе к дочернему узлу: добавить ребро в `pathEdges`, добавить узел в `visited`, создать кадр;
- когда кадр исчерпан: удалить узел из `visited` и удалить соответствующее входящее ребро из `pathEdges`;
- корневой кадр не должен удалять несуществующее входящее ребро.

Я бы попросил проверять инвариант:

\\[ |pathEdges| = |stack| - 1 \\]

для обычного DFS-стека с одним корневым кадром.

Это не обязательная runtime-проверка в production, но хороший ориентир для реализации и тестов. Иначе легко получить ошибку, когда после возврата из одной ветки в следующую переиспользуется остаток предыдущего пути.

### 2. Отдельно проверить `CYCLE_DETECTED`

Вот здесь я бы не принимал фразу «не меняется» на веру.

При переписывании DFS важно сохранить не только то, что цикл не включается в simple path, но и условия, при которых выставляется `CYCLE_DETECTED`.

Нужны как минимум три сценария:

- цикл без допустимого пути к origin;
- цикл в одной ветке, но допустимый путь в другой;
- повторное посещение узла в другой ветке, которое не является циклом текущего пути.

Последний случай особенно важен: глобальный `visited` вместо path-local `visited` изменил бы семантику. В плане заявлен один `visited`, но он должен означать именно узлы текущего пути, а не все когда-либо посещённые узлы.

### 3. Не ограничиваться двумя новыми тестами

512 родителей и цепочка из 10 000 рёбер — хорошие тесты производительности и масштабирования. Но они недостаточно проверяют сохранение поведения.

Я бы добавил:

| Сценарий                                     | Что проверяем                                            |
| -------------------------------------------- | -------------------------------------------------------- |
| Diamond merge                                | Все допустимые пути сохраняются                          |
| Дублированные edges                          | Дедупликация не создаёт лишних путей                     |
| Cycle + valid branch                         | Цикл не ломает соседнюю допустимую ветку                 |
| Повторный узел в разных ветках               | `visited` действительно path-local                       |
| ID с разделителями и NUL                     | Нет коллизий ключей и нарушений финальной сортировки     |
| Повторный запуск на одном графе              | Детерминированный результат                              |
| Изменение результата после возврата из ветки | Нет утечки состояния между DFS-ветками                   |
| Frozen path                                  | Сам массив пути и вложенные объекты действительно frozen |

Последний пункт особенно важен: сохранение `deep-frozen Path` — публично наблюдаемое свойство, а не просто деталь реализации.

### 4. Ещё один тонкий момент: какой edge остаётся после дедупликации

Нужно воспроизвести не только критерий дедупликации, но и поведение при выборе представителя.

Если два declared edge имеют одинаковые `(parent, relation)`, но различаются дополнительными полями, `edges.some()` мог оставлять первый встретившийся edge.

Новая реализация должна сохранить это поведение: первый edge побеждает, последующие дубликаты игнорируются. Не перезаписывать значение в `Map` последним дубликатом. Иначе можно незаметно изменить содержимое результирующего пути, хотя количество путей останется прежним.

Также нужно убедиться, что ключи `Map` соответствуют именно тем полям, которые использует существующая дедупликация, а не случайно сравнивают объекты по ссылочной идентичности.

## Важная оговорка по сложности

После изменений можно ожидать:

- построение adjacency — ожидаемо \\(O(E)\\) плюс сортировка;
- хранение состояния DFS — \\(O(D)\\), где \\(D\\) — глубина текущего обхода;
- материализация результатов — пропорциональна суммарному размеру возвращаемых путей.

Но общая сложность `collectPaths()` не становится линейной. Количество simple paths в графе слияний может быть экспоненциальным. Это ограничение #25, и #24 его не устраняет.

Я бы попросил не использовать в PR формулировки вроде «linear traversal» без уточнения, что именно стало линейным.

План одобряю. Перед реализацией прошу учесть несколько уточнений:

1. Backtracking должен поддерживать инвариант `pathEdges.length === stack.length - 1` (один корневой кадр). При выходе из кадра удаляются именно его узел из path-local `visited` и соответствующее входящее ребро.
2. `visited` должен содержать только узлы текущего пути, не глобально посещённые узлы.
3. Сохранить точную семантику `CYCLE_DETECTED`: проверить цикл без допустимого пути, цикл в одной ветке при наличии допустимого пути в другой и повторное посещение узла в разных ветках.
4. Дедупликация должна сохранять поведение текущего `edges.some()`, включая выбор первого edge при совпадении `(parent, relation)`. Не заменять его последним дубликатом.
5. Добавить регрессионные тесты: diamond merge, cycle + valid branch, повторный узел в разных ветках, ID с NUL/разделителями, детерминизм повторного запуска и deep-freeze результата.
6. Не заявлять линейную сложность всего collectPaths: оптимизируются построение adjacency и память DFS, но перечисление всех simple paths остаётся output-sensitive и может быть экспоненциальным.
