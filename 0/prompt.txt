## 2. Objective

Implement the **RuntimeInstance lifecycle decomposition (D-1)**.

The task introduces the minimal structural representation needed to distinguish:

- a RuntimeInstance;
- its lifecycle state;
- events associated with its lifecycle;
- the immutable descriptor describing that runtime.

The implementation must preserve the distinction between a runtime lifecycle event and a change to the runtime's identity or authority.

The intended result is a small, testable Core implementation — not a general event-sourcing framework or a runtime orchestration system.

## 3. Required scope

### A. RuntimeInstance registry / entity extension

Extend the existing entity model with the registry and minimal RuntimeInstance representation required by D-1.

Requirements:

- Reuse existing Core primitives, identifiers, ownership rules, validation patterns, and export conventions.
- Preserve the distinction between Participant, Identity Version, Runtime Instance, and Authority Principal.
- Do not collapse RuntimeInstance identity into Participant identity.
- Do not infer identity continuity or authority inheritance from runtime lifecycle events.
- Apply existing construction-time validation, defensive copying, and deep-freeze conventions.
- Do not introduce `any` or expose unvalidated `unknown` through public domain APIs.

Keep the model minimal. Do not add fields or lifecycle states merely because they might be useful in a future implementation.

### B. Minimal runtime event record

Introduce the minimal runtime event record required by D-1.

The record must support the separation of lifecycle events from the RuntimeInstance descriptor.

Important:

- The descriptor must remain byte-identical when a lifecycle event occurs.
- An event must not silently mutate or replace the descriptor.
- Do not embed future event-format decisions into the implementation.
- The event format is deferred to CORE-002. Do not design or implement CORE-002 as part of this task.

Use only the event semantics established by the approved plan and CORE-001. Do not invent additional event types, ordering guarantees, delivery semantics, persistence guarantees, or replay behavior.

### C. Separate failure event from runtime state

Implement the D-1 distinction between the failure event and the runtime's lifecycle state.

The conformance requirements explicitly include:

- **rt-1:** a failure event is represented separately from the runtime lifecycle state.
- **rt-2:** the RuntimeInstance remains `RUNNING` in the specified scenario; recording a failure event must not implicitly transition it to another lifecycle state.

Do not interpret the presence of a failure event as automatic termination, revocation, invalidation, or loss of authority.

The event records what happened. It does not, by itself, decide what the system must do next.
