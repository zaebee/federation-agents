1. Findings
F-01. No-op adapter path обходит Core admission и возвращает mutable state
P2 — исправить до merge
Файл: src/adapters/orphan-assessment.ts:127–128

Сейчас:
if (candidates.length === 0) {
  return { ok: true, value: { assessments: [], registered: request.existing } };
}


Это обход Core admission.

В результате:
- registered ссылается непосредственно на массив вызывающей стороны;
- массив и содержащиеся в нём объекты могут оставаться mutable;
- исходный массив не копируется;
- существующие записи не проходят даже проверку duplicate IDs;
- поведение отличается от обычного успешного пути, где Core возвращает новую frozen representation.
Причём тест явно закрепляет aliasing:
expect(result.value.registered).toBe(existing);


Это противоречит выбранной модели владения: Core должен возвращать immutable registered representation.

Предлагаемое исправление:

Не обходить Core при пустом batch. Вызвать:
const admitted = registerOrphanAssessments(
  candidates,
  request.graph,
  request.existing,
);


Даже когда candidates пустой. admitAssessments уже умеет копировать и замораживать существующее состояние.

Дополнительно заморозить результирующий OrphanAssessmentEmission.

Нужен тест:
1. Передать mutable existing с mutable Assessment.
2. Вызвать адаптер для графа без orphan.
3. Изменить исходный массив и Assessment.
4. Убедиться, что возвращённый registered не изменился.
5. Проверить Object.isFrozen массива и вложенных объектов.
Это не просто косметика: сейчас результат публичного API зависит от того, нашёл ли адаптер хотя бы один orphan.

F-03. T18-DEC-15: поле Resolution всё ещё неудачно названо
P3 — документационное уточнение
Файл: decision-register.md:20,36

В таблице по-прежнему есть колонка Resolution, а в ней:
OPTION-B-LOCAL (local implementation choice/disposition)


Статус правильно оставлен OPEN, а пояснение в §3 тоже правильное.

Но мы специально договорились не использовать термин resolution для локального выбора, чтобы не создавать впечатление нормативного разрешения.

Предлагаю для этой записи использовать Local implementation disposition либо изменить значение на OPTION-B-LOCAL (non-normative).

Не блокирует реализацию, но лучше устранить неоднозначность сейчас.

3. Отдельно о Core admission
В assessment.ts я проверил:
- validateContinuityAssessment;
- validateOrphanAssessment;
- registerOrphanAssessments;
- admitAssessments;
- сохранение supersession history.
Основной алгоритм корректен:
1. Все кандидаты проходят generic validation.
2. Все кандидаты проходят C-1 contextual validation.
3. Проверяются ID и supersession-связи на полном prospective state.
4. Только после этого возвращается новая frozen representation.
При ошибке исходный existing не изменяется.

Есть одно архитектурное ограничение, которое стоит помнить: Core contextual validator проверяет именно C-1 семантику. Он не является универсальным валидатором всех возможных Claims в Assessment. Остальные Claims остаются частью модели доверия к Assessment и локальной политики. Это соответствует текущей архитектуре, но не следует описывать admission как полную семантическую верификацию документа.
