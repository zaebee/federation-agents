# Task 11 — Corrected Decisions: Scope × Immediate Merge Closure

Two implementation/plan contradictions have been identified by exercising the actual Task 10 APIs. Apply the following decisions before completing Task 11.

## Decision 1 — Scope applies to discovery, not closure

**Keep Task 10 implementation unchanged. Preserve approved C1 semantics.**

Scope filters which edges can be traversed during path discovery. Once a merge node is present on a discovered path, immediate closure validates all direct parent edges of that node, regardless of relation type or whether those edges are included in the discovery scope.

Consequences:

- Under `CONTINUATION_ONLY` and `CONTINUATION_AND_FORK`, a pure merge-dependent candidate remains unreachable and fails with `ERR_NO_TRAVERSAL_PATH`.
- Under either restricted scope, a mixed-relation merge node may still be reached through a scope-permitted edge.
- Such a node is still recognized as a merge node from full graph adjacency.
- Its closure checks every direct parent edge, including scope-excluded `MERGED_FROM` edges.
- Therefore `ERR_MERGE_BRANCH_UNSATISFIED` is reachable under restricted scopes for mixed-relation merge nodes.

Update `tests/unit/scope-matrix.test.ts` accordingly:

1. Retain tests proving that discovered paths contain only scope-permitted edges.
2. Retain pure merge candidate discovery failures under restricted scopes.
3. Add mixed-relation regression fixtures for both `CONTINUATION_ONLY` and `CONTINUATION_AND_FORK`.
4. Verify that a path discovered through a permitted `CONTINUATION` edge can fail immediate closure because another direct parent edge of the same merge node lacks an applicable/satisfactory assessment.
5. Assert the exact top-level result and per-path closure details.

Remove the incorrect invariant that closure failure is structurally unreachable under restricted scopes.

Do not make closure scope-aware. Do not alter Task 10 production code.

## Decision 2 — Terminal origin merge node is excluded from immediate closure

**Preserve current Task 10 behavior. Do not implement origin inclusion.**

`validateMergeClosure` currently checks merge nodes represented as `edge.child` along the selected path. The terminal origin is not processed as a child edge and its parent branches are not closed.

Update `tests/experimental/origin-merge-closure.test.ts` to pin this actual behavior:

- origin is a `MERGED_FROM` node;
- selected path terminates at origin;
- origin's parent edges are not checked by immediate closure;
- if all other path checks pass, binding may remain eligible;
- test is explicitly BLOCKED / non-conformance under A-11.

Do not move this test into conformance coverage.

Do not change production code to include the origin.

A-11 remains BLOCKED. This test documents implementation behavior; it does not resolve the normative ambiguity.

## Documentation changes

Update the Task 11 section in:

`docs/superpowers/plans/2026-10-30-uia-core-001-implementation.md`

Correct all statements that imply:

- closure failure is impossible under restricted scopes;
- closure only checks parent edges permitted by the discovery scope;
- the conservative default includes the terminal origin.

Document the two distinct rules explicitly:

1. Scope governs discovery.
2. Immediate closure checks all direct parent edges of merge nodes encountered as path children, independently of discovery scope; the terminal origin is currently excluded.

Preserve A-11 as BLOCKED and preserve the existing normative specification unchanged.

Review Global Constraint 13 references in the implementation plan. Correct implementation-plan interpretations that conflict with approved C1 semantics, but do not silently rewrite normative CORE-001 text. If the normative text itself appears inconsistent with the approved implementation decision, flag the exact passage as a separate specification issue rather than resolving it in this task.

План в целом согласуется с двумя принятыми решениями Task 11. Я бы перед передачей build-агенту внёс две небольшие, но важные поправки.

### 1. Уточнить критерий FULL_ANCESTRY

Сейчас написано:

> closure failures для merge-узла равны его прямым parent-рёбрам из graph.edges, минус точное ребро пути.

Это слишком сильное утверждение. Closure failures — не список всех проверенных ветвей, а список ветвей, на которых проверка завершилась неудачей. Если для какой-то ветви есть подходящий assessment и assurance проходит, она не должна попасть в failures.

Лучше разделить два утверждения:

- closure проверяет все прямые parent-рёбра merge-узла, кроме точного ребра, уже проверенного Phase 2;
- `failures` содержит только те из проверяемых ветвей, которые не прошли closure, с соответствующими причинами.

### 2. Проверить ожидание `closure: SATISFIED` в origin-тесте

В `PathOutcome` поле `closure` опционально. В фикстуре `C → O`, где `C` не merge-узел, а `O` — терминальный origin, closure может вообще не запускаться.

Поэтому ожидание:

> outcome: VALID; closure: SATISFIED

нужно сверить с фактическим контрактом `evaluateBinding` и Task 10. Если closure не запускался, корректное ожидание — `closure` отсутствует. Это не меняет саму проверку A-11: родители `O` не закрываются, а binding остаётся eligible.

Не стоит искусственно создавать `SATISFIED` только ради удобства теста: отсутствие closure и успешно выполненный closure — разные состояния.

- Проверки pure merge candidate и mixed-relation merge под обоими restricted scopes — нужные регрессии.
