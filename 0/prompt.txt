# Task 16 — Implementation Reference Documentation

Repository: `zaebee/federation-agents`  
Plan: `docs/superpowers/plans/2026-10-30-uia-core-001-implementation.md`  
Plan revision: Rev E (0.3.3)  
Normative source: `docs/CORE-001.md` — UIA-CORE-001 Rev 0.3.3

## Objective

Implement Task 16 from the approved Rev E plan.

Create `docs/implementation.md`: a technically accurate reference for the existing UIA-CORE-001 reference implementation.

This is a **documentation-only task**. Document what the code actually does, distinguish normative semantics from implementation mechanisms, and preserve every unresolved ambiguity.

Do not implement new functionality or silently resolve any normative gap.

## 1. Mandatory preflight

Before writing:

1. Read the complete `docs/CORE-001.md`.
2. Read the complete approved implementation plan.
3. Inspect the current source tree under `src/core/`, `src/index.ts`, tests, package scripts and existing documentation.
4. Verify that Tasks 1–15 are present in the current merged code.
5. Compare actual exported APIs and implementation behavior against the plan.
6. Identify discrepancies between:
   - normative CORE-001 text;
   - approved implementation decisions;
   - actual source code;
   - tests and conformance assertions.

Do not assume the plan is perfectly synchronized with the merged implementation.

If a discrepancy exists, document the actual state and report it. Do not modify production code to make documentation easier.

## 2. Required document structure

Create exactly:

`docs/implementation.md`

The document must contain the following sections.

### 2.1 Architecture overview

Describe:

- project purpose and scope;
- module structure;
- responsibility of every `src/core/` module;
- public API boundaries and exports;
- data flow through the library;
- immutable ownership model;
- error/result model;
- runtime portability and dependency constraints.

Include a Mermaid diagram if it materially clarifies module relationships or data flow.

Distinguish domain entities from implementation infrastructure.

Explicitly state that this is a pure reference implementation of CORE-001, not a complete distributed UIA runtime.

### 2.2 Module and API reference

For every actual module in `src/core/`, document:

- responsibility;
- important public types;
- exported functions;

- `Evidence` and `Assessment`;

- identity/version/runtime descriptors and runtime lifecycle events.

Do not imply that the implementation provides full CORE-002, CORE-003 or CORE-004 functionality.

### 2.3 Three traversal phase contracts

This section is mandatory and must be technically precise.

Document the three independently testable phases:

1. **Discovery** — deterministic, scope-filtered path discovery.
2. **Validation** — per-edge/path validation and assurance evaluation.
3. **Immediate merge closure** — checking direct parent edges of merge nodes on a selected path.

For each phase, describe:

- contract and inputs;
- output/result types;
- ordering and determinism;
- failure semantics;
- immutability guarantees;
- relevant tests.

Specifically explain:

- memoized DFS and its intended soundness;
- cycle detection and guards;
- how the implementation avoids dependence on insertion order;
- GC-18 per-path outcome retention;
- why top-level error aggregation is an implementation aggregation, not a normative precedence table;
- the B-4 derivation of the one pinned aggregation behavior;
- immediate closure versus recursive closure.

**Critical:** The implementation checks immediate closure only. Recursive closure is BLOCKED and must not be described as implemented or conformant.

Also explain the scope/closure distinction:

- scope governs discovery;
- closure is scope-independent;
- a mixed-relation merge node reached through a permitted edge is still recognized as a merge node;
- all direct parent edges of that node are checked;
- a candidate reachable only through a hidden relation still fails discovery.

Document the terminal-origin behavior as unresolved A-11, not as a normative conclusion.

### 2.6 Ambiguities Register v5

### 2.7 Mechanisms versus semantics

This section is mandatory.

Explicitly distinguish normative protocol semantics from replaceable implementation mechanisms.

Cover at least:

- in-memory ledger;
- replaceable default policies;
- versioned selector mechanism `uia-ref-selector@1`;
- pure TypeScript SHA-256;
- crypto verifier test doubles;
- ledger/test fixtures;
- seeded property generators;
- external temporal trust assessment.

For each mechanism, explain:

1. What it does.
2. What it does NOT establish.
3. Whether it is replaceable.
4. What versioning or compatibility implications exist.
5. Which assessments or results must identify the mechanism/version they depend on.

Important boundaries:

- The in-memory ledger is not a CORE-002 event format or distributed ledger.
- A signature verifier outcome does not establish identity, authority, or trust in a timestamp.
- SHA-256 implementation is replaceable; canonicalization and hashing semantics are pinned by the relevant standards and CORE-001 projection.
- Selector grammar is an implementation mechanism and carries its own version label.
- Temporal trust is externally assessed. The core does not establish timestamp trust itself.
- The five standard timestamp kinds do not exhaust timestamp-bearing fields. Non-standard fields such as `compromise_effective_at` are keyed by `TemporalFieldRef`.

### 2.8 Proposed minimal normative clarifications

Collect the BLOCKED items from the ambiguities register into a separate section.

- implementation consequences of each alternative.

These are proposals for future specification work, not implemented behavior.
