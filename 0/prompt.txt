## 1. Objective

Implement §9 Local Acceptance and its lifecycle, with particular attention to D-2:

- A Local Acceptance Record is an immutable normative act issued by a domain.
- Lifecycle events are separate records and MUST NOT mutate the original acceptance decision.
- Lifecycle transitions are evaluated relative to the previous state and an explicitly injected local policy.
- There is no universal automatic transition policy.
- Historical decisions and assessments remain preserved even when later events or assessments change the current evaluation.
- A later credential revocation or superseding assessment must not rewrite historical rulings.
- Local Acceptance is contextual; it is NOT a universal prerequisite for interactions and is NOT an Authority Grant.

This is a pure reference implementation, not a distributed event system.

## 4. Lifecycle model — §9.3

Implement the normative states:

```ts
type AcceptanceLifecycleState =
  | 'ACTIVE'
  | 'SUSPENDED'
  | 'REINSTATED'
  | 'REVOKED'
  | 'EXPIRED';
```

Implement the lifecycle event with exactly the normative fields:

```ts
interface LocalAcceptanceLifecycleEvent {
  event_id: string;
  acceptance_id: AcceptanceID;
  new_state: AcceptanceLifecycleState;
  transition_reason: string;
  evidence_refs: string[];
  effective_at: Timestamp;
}
```

Lifecycle event validation must follow the same strict boundary and ownership rules as other public records.

**Critical invariants:**

1. An event MUST NOT mutate the corresponding `LocalAcceptanceRecord`.
2. An event MUST NOT replace or rewrite an earlier event.
3. An event is a separate historical record.
4. A transition is evaluated relative to the previous lifecycle state.
5. Transition validity is determined only by an injected local policy.
6. The implementation MUST NOT invent a universal state-transition table or default policy.
7. `effective_at` is a declared timestamp, not evidence that the timestamp is trusted.
8. Timestamp selection follows `TemporalContext.basis`; timestamp trust remains a separate external assessment.

Do not silently infer transition validity from enum ordering, timestamps, or event arrival order.

## 5. Lifecycle API

Implement the plan's interface:

```ts
applyLifecycle(
  record: DeepReadonly<LocalAcceptanceRecord>,
  event: DeepReadonly<LocalAcceptanceLifecycleEvent>,
  previousState: AcceptanceLifecycleState,
  ctx: TemporalContext,
  policy?: LifecyclePolicy,
): Result<AcceptanceLifecycleState>
```

The exact `LifecyclePolicy` shape should be derived from the existing `Policy` and temporal conventions in the repository. Keep it minimal and explicitly typed.

Requirements:

- Validate that the event refers to the supplied acceptance record.
- Validate the input records and relevant lifecycle state.
- Use `TemporalContext.basis` to select the declared timestamp relevant to the lifecycle query.
- Do not derive timestamp trust from timestamp presence.
- Do not treat `effective_at` as trusted merely because it exists.
- When a policy is supplied, use it to determine whether the proposed transition is valid relative to `previousState`.
- Do not invent transition rules when policy is absent.
- Return a discriminated `Result`; do not use exceptions or bare booleans for semantic failures.
- Preserve the normative/mechanism error distinction.

**No implicit policy:** absence of a policy must not silently mean “allow all transitions” or “deny all transitions” as a universal semantic rule. Follow the approved plan's explicit distinction: lifecycle events can be recorded without a transition policy, but lifecycle queries require an explicit policy.

If the exact behavior of an absent policy at a particular API boundary is not fully determined by the plan or spec, document the ambiguity and keep the mechanism conservative. Do not resolve it by inventing normative semantics.

## 8. D-2 — required conformance scenario

Implement D-2 in `tests/conformance/d.test.ts`.

Scenario:

1. A Credential is used for a historical action.
2. An initial assessment supports a historical ruling/acceptance decision.
3. A Local Acceptance Record is created and stored.
4. Preserve a deep snapshot of:
   - the original acceptance/ruling record;
   - the original supporting assessment;
   - the corresponding historical ledger state.
5. Later, a `CredentialRevocationRecord` is registered.
6. A new superseding `ContinuityAssessment` is registered, reflecting compromise or a contested historical basis.
7. Perform a fresh evaluation using the updated information.
8. The fresh evaluation must be able to return a compromised/contested result according to the existing Task 13 semantics and applicable policy.
9. Verify that all historical records remain unchanged.

Required assertions:

- The original Local Acceptance Record is byte-identical before and after later events.
- The original supporting assessment is byte-identical before and after supersession.
- The original historical ruling/decision remains in the ledger.
- The later lifecycle/revocation/assessment records are additional records, not replacements.
- Fresh evaluation reflects the new evidence/assessment state.
- Historical decision preservation does not force the fresh evaluation to remain positive.
- No credential or identity descriptor is deleted or rewritten.
- No authority grant is created, revoked, or inherited by this task.

Do not fake the fresh compromised/contested result with a hardcoded Task 15 outcome. Reuse Task 13's actual evaluation semantics and explicit policy inputs.

If the exact relationship between a CORE-001 Local Acceptance Record and a CORE-004 Ruling is not represented in the current model, preserve the distinction. Do not invent a CORE-004 Ruling type or claim that Local Acceptance implements the full CORE-004 model. Use the plan's D-2 terminology and explicitly document the boundary.

Остальные предложенные границы тоже поддерживаю:

### Два небольших замечания перед реализацией

1\. Исключения из policy callbacks.

Если `allowsTransition()` или `isApplicable()` выбрасывает исключение, это должно быть mechanism failure, а не `REJECTED`. Иначе сбой исполнения политики будет неотличим от осознанного отказа. Не возвращать частичный результат.
