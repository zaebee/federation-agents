## Mode

**PLAN MODE ONLY.**

Do not modify files, create commits, open PRs, change tests, or alter implementation. This task is verification and audit planning only.

## Context

We have completed implementation Tasks 1–15 and documentation Task 16 for UIA-CORE-001 Rev E (0.3.3).

Relevant repository artifacts:

- Normative specification: `docs/CORE-001.md`
- Implementation reference: `docs/implementation.md`
- Architecture overview: `docs/ARCHITECTURE.md`
- Approved implementation plan: `docs/superpowers/plans/2026-10-30-uia-core-001-implementation.md`
- Implementation: `src/core/`
- Conformance tests: `tests/conformance/`
- Unit and property tests: `tests/`

Task 16 produced an evidence-backed implementation reference. It explicitly distinguishes normative semantics, implementation mechanisms, test coverage, and unresolved ambiguities.

Known baseline at the beginning of Task 16:
- 511 tests total
- 507 passing
- 4 todo
- 3283 assertions
- `format:check` passing

Treat these as historical baseline figures, not guaranteed current results. Re-run verification and report actual results.

## Objective

Perform a complete, assertion-level conformance audit of the current implementation against `docs/CORE-001.md` Rev E (0.3.3).

The central question is:

**Does the implementation satisfy each normative requirement of CORE-001, and what evidence supports that conclusion?**

This is not a code-quality review, refactoring exercise, or feature-development task.

## Non-negotiable principles

1. **Specification is the normative authority.** Do not treat implementation behavior, tests, or the implementation plan as substitutes for normative requirements.

2. **Evidence ≠ Finding ≠ Ruling ≠ Execution Authorization.** Preserve these distinctions throughout the audit.

3. Do not infer conformance from test success alone. A passing test may be incomplete, weak, or test the wrong property.

4. Do not infer non-conformance merely because a behavior is not implemented if the specification leaves it OPEN or BLOCKED.

5. Do not resolve normative ambiguity through implementation behavior or personal interpretation. Record it as OPEN/BLOCKED and explain why it prevents a conformance judgment.

6. Do not silently reconcile contradictions between:
   - `docs/CORE-001.md`
   - `docs/implementation.md`
   - source code
   - tests
   - approved implementation plan

   Identify the conflicting statements and their provenance.

7. Do not change normative semantics, add requirements, or invent new conformance criteria.

8. Do not modify production code or tests, even when you find defects. Report findings separately.

9. Do not claim full conformance if any applicable requirement is FAIL, PARTIAL, BLOCKED, or NOT COVERED.

10. Do not create new normative error codes, APIs, authority mechanisms, revocation semantics, or recursive closure behavior as part of this task.

## Scope

### A. Normative requirement inventory

Read the complete `docs/CORE-001.md`.

Extract every normative requirement, including:
- MUST / MUST NOT
- SHALL / SHALL NOT
- REQUIRED / PROHIBITED
- explicit invariants and constraints
- normative field and type requirements
- validation and rejection requirements
- temporal semantics
- authority and trust boundaries
- lifecycle semantics
- cryptographic and provenance claims
- explicit OPEN/BLOCKED items and limitations

Do not restrict the inventory to §12 conformance cases.

Assign stable audit identifiers such as `N-001`, `N-002`, etc. These are audit identifiers only, not new specification identifiers.

For each requirement record:
- specification section and exact text or a concise faithful paraphrase;
- normative strength;
- applicability;
- relevant implementation module(s);
- relevant test(s);
- verification method;
- current assessment status;
- evidence and reasoning.

### B. §12 conformance case audit

Audit all 18 conformance cases in §12.

Known coverage caveat:
- C-1 and C-2 have `test.todo` entries.
- There are partial graph-level tests, but these must not be presented as full conformance coverage.
- Task 16 documented 16/18 cases as covered; independently verify this against current files.

For every case:
1. Identify each individual assertion in the normative case.
2. Locate the corresponding test(s), if any.
3. Inspect the actual assertion and its setup.
4. Trace the behavior to the implementation.
5. Determine whether the test genuinely proves the normative property.
6. Identify missing negative cases, boundary cases, or adversarial cases where relevant.
7. Assign a status and explain it.

Do not use a single status for a case if its individual assertions have different outcomes. Preserve assertion-level granularity.

### C. Implementation traceability

Inspect relevant source code, not just exported API declarations.

Trace each requirement through:
- public API;
- runtime validation;
- internal mechanism;
- state transition or result construction;
- error behavior;

- Global Constraint 17: no public domain record or semantic result may expose unvalidated `unknown`; no exported API may use `any`.
- Temporal trust keyed by `(subject_ref, field)` and timestamp semantics.
- `ApplicableAssessments` nominal branding and runtime validation.
- B-5 adversarial policy narrowing and exclusion of untrusted assessments.
- Merge closure semantics, including mixed relation edges and direct-parent checking.
- Immediate closure vs recursive closure.
- A-11 origin closure and terminal-origin treatment.
- Credential revocation and historical signature evaluation.
- Runtime lifecycle decomposition.
- Local Acceptance record vs lifecycle ledger.
- Separation of identity lineage from authority inheritance.
- No grant-producing API.
- No blanket automatic revocation.
- No implicit authority transfer.

Do not assume that the existence of a type, brand, helper, or test establishes the full normative property.

- experimental tests are incorrectly counted as conformance coverage.

Preserve the specification's existing ambiguity identifiers and statuses.

- a Finding into a Ruling;
- Local Acceptance into a Ruling;

Do not fix failures.

## Required audit statuses

Use exactly these statuses:

- `PASS` — requirement is sufficiently supported by implementation and adequate verification evidence.
- `FAIL` — implementation demonstrably violates an applicable normative requirement.
- `PARTIAL` — some but not all parts of the requirement are implemented or verified.
- `BLOCKED` — a normative ambiguity or missing decision prevents a valid conformance judgment.
- `NOT COVERED` — no adequate verification evidence exists. This does not automatically mean implementation is wrong.

Keep implementation status and verification status distinguishable. For example, a requirement may appear implemented but remain NOT COVERED due to missing tests.

Do not use `PASS` where evidence is only indirect.
