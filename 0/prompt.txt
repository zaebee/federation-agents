### Blocker 1 — mixed CONTESTED + INVALID aggregation

Current code uses:

```ts
failed.every((item) => item.outcome.status === 'CONTESTED')
```

This contradicts the approved Task 9 decision.

Required behavior:
- Any VALID path → `eligible: true`.
- No VALID paths, but at least one CONTESTED path → `kind: 'CONTESTED'`.
- No VALID or CONTESTED paths → ordinary normative failure.

Add a regression test with two paths: one CONTESTED, one INVALID. The result must be CONTESTED, and both per-path outcomes must remain present.

Do not introduce a new UiaErrorCode or close A-8.

### Blocker 2 — Global Constraint 18 is violated on success

Current successful BindingResult contains only `acceptedPaths`. When one path is VALID and another is INVALID or CONTESTED, the failed path outcome is discarded.

Global Constraint 18 requires every per-path outcome to be preserved in `BindingResult.details.perPath`, independently of the top-level aggregation.

Extend the successful BindingResult variant to retain all per-path outcomes, including both accepted and rejected paths. Keep `acceptedPaths` if useful for callers, but do not discard failed path details.

Add a regression test:
- two discovered paths;
- one VALID;
- one INVALID;
- `eligible === true`;
- both outcomes are present in `details.perPath`.

Also test VALID + CONTESTED if practical.

### Medium finding

**Location:** `src/core/traversal.ts:232-234`

Under `FULL_ANCESTRY`, 30 stacked diamonds plus a disconnected registered origin require only 92 nodes, but this push re-explores shared ancestry for every prefix, causing billions of visits before returning `ERR_NO_TRAVERSAL_PATH`. Because `evaluateBinding` calls discovery synchronously (`src/core/traversal.ts:390`), a small valid graph can stall evaluation despite producing no paths. Precompute scope-filtered reachability to the origin or otherwise prune shared dead subgraphs.

### Medium finding

**Location:** `src/core/traversal.ts:212-217`

For `V1 → V2 → V1`, selecting V1 as candidate and V2 as origin accepts `[V1→V2]` before examining the back edge. `buildLineageGraph` preserves and flags this cycle (`src/core/lineage.ts:344–349`), but a trusted assessment on V1→V2 makes `evaluateBinding` return `eligible:true` (`src/core/traversal.ts:401–414`). Reject paths using detected cyclic segments and preserve the `CYCLE_DETECTED` outcome.

### Medium finding

**Location:** `src/core/traversal.ts:199-238`

`discoverPaths` lists every simple candidate→origin path and keeps them all in memory, with no limit on path count or depth. `evaluateBinding` then runs `validatePath` on each one, which deep-copies all assessments for every edge. A participant who publishes descriptors forming a chain of k merge diamonds (`MERGED_FROM` under `FULL_ANCESTRY`, about 3k nodes) produces 2^k paths, so evaluating a binding for their candidate can hang or run out of memory. Fix: cap the number of paths and the work done, returning a mechanism failure when the cap is hit, or answer reachability and validity without listing every path.
