## 3. Structural validation requirements

## Approved decisions

1. `validateDescriptor` accepts `DeepReadonly<IdentityVersionDescriptor>`. The caller must first pass untrusted input through `validateIdentityVersionDescriptor`. `validateDescriptor` is a structural validator, not a second boundary-validation path. Add a composition test proving the intended call sequence. Remember that `DeepReadonly` is a compile-time contract, not runtime provenance proof.

2. `Registry` exposes readonly collections:
   - `readonly DeepReadonly<ParticipantRecord>[]`
   - `readonly DeepReadonly<IdentityVersionDescriptor>[]`

3. Missing parent: skip same-participant validation when the parent is absent from Registry. This is delayed-parent handling and belongs to Task 7. Do not reject solely because the parent is missing. Always reject self-parent references, regardless of Registry contents.

4. Duplicate IDs in Registry: use deterministic first-match lookup (`find`). Document that Registry is assumed consistent. This is an implementation assumption, not a normative UIA rule. Do not invent a new error code or duplicate-ID rejection behavior.

5. Use these public validator names:
   - `validateParticipantRecord`
   - `validateCredentialDescriptor`
   - `validateLineageLink`
   - `validateRuntimeInstanceDescriptor`

   Reuse internal validators. Do not introduce weaker or parallel validation paths.

## Structural rules

- `CONTINUATION`: exactly 1 parent.
- `FORKED_FROM`: exactly 1 parent.
- `MERGED_FROM`: at least 2 parents.
- Empty lineage is valid.
- Mixed relation arrays are valid unless the normative spec explicitly prohibits them.
- Self-parent: `ERR_INVALID_RELATION`.
- Cross-participant CONTINUATION with a known parent: `ERR_INVALID_RELATION`, including `parent_version_id`.
- Cardinality violation: `ERR_INVALID_CARDINALITY`, without `parent_version_id`.
- Preserve the exact planned `StructuralResult` union.
- Never normalize, remove, or rewrite declared lineage links.
